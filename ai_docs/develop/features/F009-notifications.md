# F009: Уведомления

**Дата:** 2026-06-01  
**Статус:** MVP (минимально) — расширяется отдельной темой

## Цель

Поставщик (и при желании снабженец) получает email о ключевых событиях. Уведомления — **отдельная подсистема**, в MVP реализуем минимум по email с opt-in в личном кабинете.

## Принцип

- Уведомления **выключены по умолчанию**.
- Пользователь в ЛК включает тумблер и вводит email → начинают приходить письма.
- Каналы помимо email (Telegram, push) — вне MVP, но модель не должна мешать их добавить.

## Настройки в профиле (`profiles`)

| Поле | Описание |
|------|----------|
| `notify_email` | Куда слать (может отличаться от логина) |
| `notify_on_new_request` | Новый запрос пришёл поставщику |
| `notify_on_completed` | Запрос завершён (победа/брак/итог) |

## События MVP

| Событие | Кому | Тип |
|---------|------|-----|
| Новый запрос направлен поставщику | поставщику invite | `new_request` |
| Запрос завершён (won/lost/cancelled/no_response) | поставщику invite | `request_completed` |

Снабженцу уведомления — опционально (та же модель), приоритет ниже.

## Доставка

- Очередь `notifications` (см. data-model.md): запись `pending` → отправка → `sent` / `failed`.
- Отправка: Supabase Edge Function + почтовый провайдер (Resend/SMTP) — выбрать при реализации.
- Идемпотентность: не слать дубликаты по одному событию.

## UI

- В ЛК поставщика раздел «Уведомления»: тумблеры + поле email + проверка формата.
- Снабженец/админ: те же настройки в профиле.

## Вне MVP

- Telegram/push, дайджесты, настройка частоты, шаблоны писем в админке.

## Критерии приёмки

- [ ] По умолчанию писем нет
- [ ] При включённом `notify_on_new_request` поставщик получает письмо о новом запросе
- [ ] При завершении запроса приходит письмо, если включено
- [ ] Нет дублей по одному событию
