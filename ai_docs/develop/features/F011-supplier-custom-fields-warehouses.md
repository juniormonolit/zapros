# F011: Поставщики как гибкая БД (кастомные поля) + Склады

**Дата:** 2026-06-02
**Статус:** Проектирование (реализация — Фаза 7.7, ПОСЛЕ Фазы 3)

## Цель

Превратить «Поставщиков» в гибкую базу: админ добавляет поля по мере необходимости
(в т.ч. мультивыбор из заданного им списка и поля с масками ввода). У каждого поставщика —
сущность «Склады» с адресом, режимом работы и правилами привязки номенклатур (задел под
будущий мэтчинг номенклатур/историю цен).

## Решения (приняты с пользователем)

- **Хранение значений — EAV** (`supplier_field_values`, строка на поле). Лучше для фильтрации/отчётов.
- **Ядро + кастом сверху**: `name`, контакты (`contact_person/phone/email/notes`), `sourcing_status`,
  `works_in_zapros` остаются колонками; кастомные поля — поверх.
- **Режим работы склада — свободный текст** (MVP).
- **Приоритет: после Фазы 3** (сначала ядро сквозного потока — запросы).

## A. Кастомные поля (admin-конфигурируемая схема)

### Схема: `supplier_field_definitions`
Админ создаёт/редактирует поля: `key`, `label`, `field_type`, `options`, `mask`,
`is_required`, `sort_order`, `is_active` (см. data-model.md).

### Типы полей (MVP)
- `text` — обычный текст.
- `masked_text` — текст с маской (`mask`), напр. телефон `+7 (999) 999-99-99`, ФИО.
- `number`, `date`, `boolean`.
- `single_select` — один из `options`.
- `multi_select` — несколько из `options` (галочки). Пример: «Форма оплаты»
  `["С НДС","Без НДС","Нал"]` — старший снабженец отмечает, как поставщик может работать.

### Значения: `supplier_field_values` (EAV)
- UNIQUE `(supplier_id, field_id)`; `value jsonb` (скаляр или массив для `multi_select`).
- Валидация в server actions: соответствие типу, допустимость вариантов (для селектов),
  применение/проверка маски (для `masked_text`), обязательность (`is_required`).

### Кто редактирует
- **Админ** — управляет схемой (определения полей) и значениями.
- **Старший снабженец** — заполняет значения в карточке поставщика (в рамках проработки).
- RLS: запись значений — `is_senior_or_admin()`; управление схемой (`field_definitions`) — admin.

## B. Склады поставщика

### `supplier_warehouses`
- Поля: `name` (напр. завод/площадка), `address`, `working_hours` (текст), `sort_order`.
- У поставщика может быть несколько складов.

### Правила номенклатур: `warehouse_nomenclature_rules`
- Список предикатов: `match_type` (`contains`/`starts_with`/`ends_with`/`equals`/`regex`) + `value`.
- Пример: поставщик «Стройпоставка», склады = заводы кирпича; номенклатура содержит признак
  завода в названии. Склад «ЛСР» → правило `contains "ЛСР"`.
- **Сейчас только хранятся.** Применяются позже (Фаза задела номенклатур): номенклатура,
  совпавшая с правилом, авто-привязывается к складу → поставщику → истории цен.

## UI (Фаза 7.7)

- **Админ → Поставщики → Настройка полей**: CRUD `supplier_field_definitions` (тип, варианты, маска).
- **Карточка поставщика**: динамический рендер кастомных полей по схеме (селекты/чекбоксы/маски);
  вкладка «Склады» — CRUD складов + правил номенклатур.

## Зависимости и порядок

- Модель: `data-model.md` (`supplier_field_definitions`, `supplier_field_values`,
  `supplier_warehouses`, `warehouse_nomenclature_rules`).
- Опирается на Фазу 2.6 (роль `senior_procurement`, ядро suppliers, RLS).
- **Реализуется после Фазы 3** (запросы) — Фаза 7.7 в плане MVP.
- Готовит почву для задела «номенклатуры + история цен».

## Критерии приёмки (для будущей фазы)

- [ ] Админ создаёт поле любого из типов (вкл. `multi_select` с вариантами и `masked_text` с маской).
- [ ] В карточке поставщика поля рендерятся по схеме; значения валидируются и сохраняются (EAV).
- [ ] «Форма оплаты» как `multi_select` — галочки сохраняются массивом.
- [ ] У поставщика можно завести склады (адрес/режим/правила номенклатур).
- [ ] Правила складов сохраняются (`contains "ЛСР"` и т.п.) и готовы к будущему мэтчингу.
