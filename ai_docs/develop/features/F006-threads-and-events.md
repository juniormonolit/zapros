# F006: Треды и события

**Дата:** 2026-06-01  
**Статус:** MVP

## Цель

Коммуникация **только в рамках пары запрос–поставщик**. Чат + структурированные сигналы снабженца + системные события. Без общего чата на весь запрос (утечка между поставщиками).

## User stories

1. Как снабженец, я пишу сообщение поставщику в треде invite.
2. Как поставщик, я отвечаю в том же треде.
3. Как снабженец, я отправляю быстрый сигнал: дешевле / у заказчика дешевле / в работе.
4. Как участник, я вижу ленту: сообщения, сигналы, смена статусов, новая версия ответа.
5. При уточнении запроса в ленте появляется `request_updated` с описанием изменений.

## Модель `request_events`

| event_type | Автор | Описание |
|------------|-------|----------|
| `message` | оба | Текст в `body` |
| `signal_cheaper` | procurement | Есть цена дешевле |
| `signal_customer_price` | procurement | У заказчика дешевле |
| `signal_in_progress` | procurement | Бронь/продажа |
| `status_change` | system/procurement | payload: old/new status |
| `request_updated` | procurement | Изменение позиций/полей |
| `response_submitted` | supplier | Новая версия |

## UI

- Панель справа на карточке invite (снабженец) / внизу (поставщик).
- Быстрые кнопки сигналов + опциональное поле комментария к сигналу.
- Хронологическая лента, автор и время (Москва).

## Уточнение запроса

1. Снабженец переводит в `clarification` (invite + request).
2. Редактирует допустимые поля запроса (MVP: comment, items с предупреждением).
3. Event `request_updated` + **пауза таймера** (F007).
4. Поставщик видит изменения и может ответить новой версией.

## Realtime (опционально MVP)

- Supabase Realtime на `request_events` по `request_supplier_id` — желательно, иначе polling 30s.

## Запреты

- Нет `request_id`-level чата для поставщиков.
- `internal_note` только для снабженца — **фаза 2** (если нужно).

## Критерии приёмки

- [ ] Поставщик A не видит events invite B
- [ ] Сигналы отображаются с понятной иконкой/меткой
- [ ] Сообщение сохраняется и видно второй стороне
