## Реализация по компонентам

### Парсер

**SRC-001 + SRC-002: `src/lib/parser/bitrix.ts` + `bitrix.test.ts`**

- Парсер теперь различает **две схемы данных:**
  - **Формат A (табличный):** заголовок с колонкой «Товар» (таб-разделённые), маркер конца «Общая сумма» / «добавить чек-лист» (текущая логика, не тронута).
  - **Формат B (построчный):** строки вида `<Товар> - <Кол-во> <Ед> - <цена> руб/ед - <сумма> руб`, разделитель ` - ` (пробел-дефис-пробел), маркер конца «Итого:» или «Цена которую предлагают конкуренты:`.
- **Автовыбор:** если секция товаров табличная → формат A, иначе → формат B. Если маркер `Продукция из товаров:` отсутствует, но есть строки тире-формата → формат B.
- **Импорт:** оба формата импортируют **только** `name`, `quantity`, `unit`. **Цены и суммы не импортируются ни в формате A, ни в формате B** (как и раньше).
- **Имя товара:** может содержать запятые, числа, дефисы без пробелов. Сплит строки делается строго по ` - `, первое поле → name.
- **Тесты:** 35 старых (формат A) + 10 новых (формат B); всего **45 pass**.
- Пример кейса 113881: строка `маты прошивные МП 50, 100 мм - 1.0000 упак - 0.00 руб/упак - 0 руб` → `{ name: "маты прошивные МП 50, 100 мм", quantity: 1, unit: "упак" }`.

## Архитектурные решения и обоснование

### 1. Single source of truth для `works_in_zapros` — триггер на уровне БД

**Решение:** Стадия `sourcing_status` — мастер-данные. Флаг `works_in_zapros` — производный, синхронизируется триггером БД (миграция 008) и проверяется в server actions.

**Почему:**
- Гарантирует консистентность даже при прямом SQL-изменении (невозможно нарушить инвариант).
- Быстрые фильтры по флагу в SELECT-запросах.
- Снижает риск рассинхрона при ошибке server action.

**Реализация:** Триггер `sync_supplier_works_in_zapros` (AFTER INSERT/UPDATE) на таблице `suppliers`:
```sql
works_in_zapros := (new.sourcing_status = 'working_in_zapros')
```

### 2. Парсер с автовыбором формата

**Решение:** Функция `parseBitrixPaste` сама решает, является ли ввод форматом A (табличный) или B (построчный).

**Почему:**
- Пользователь не выбирает формат вручную — парсер детектирует по морфологии (наличие таб-разделённого заголовка, маркеры конца).
- Формат A не сломан; клиенты с текущими пейстами продолжают работать.
- Код парсера расширяемый: легко добавить формат C при необходимости.

**Эвристика:** Если блок товаров содержит строки с ` - ` разделителем ИЛИ маркер конца формата B (`Итого:`, `Цена которую предлагают конкуренты:`) → формат B. Иначе (табичный заголовок с «Товар») → формат A.

### 3. Роль `senior_procurement` между `admin` и `procurement` в enum

**Решение:** Новое значение добавлено как `BEFORE 'procurement'` (если БД-синтаксис позволяет) или просто в порядок иерархии.

**Почему:**
- Иерархия прав: `admin` (все) > `senior_procurement` (поставщики) > `procurement` (выбор) > `supplier` (ответ).
- Упорядочивает логику в условных операторах.

### 4. RLS: `procurement` видит только `available_for_selection` поставщиков

**Решение:** Политика SELECT на `suppliers` для роли `procurement` ограничена: `(sourcing_status in ('approved','working_in_zapros') and is_active)`.

**Почему:**
- Старший снабженец прорабатывает кандидатов в приватных стадиях (`new`, `called`, …); обычный снабженец не должен их видеть.
- Снижает когнитивную нагрузку: в выборе только готовые контакты.
- Безопасность: неоправданный контакт не попадёт в запрос.

### 5. Парсер НЕ импортирует цены ни в формате A, ни в B

**Решение:** `name`, `quantity`, `unit` — импортируем; `price`, `price_total` — игнорируем.

**Почему:**
- Цены из Bitrix — справочная информация для менеджера, не для поставщиков.
- Поставщик указывает свои цены в ответе, которые могут отличаться.
- Хранение raw_paste достаточно для аудита.
- Рекомендация: не показывать `raw_paste` (содержит чувствительные цены/комментарии) поставщикам; показывать только `name`/`quantity`/`unit` в запросе.

### 6. Миграция 008 как укрепление по code-review

**Решение:** После code-review, выявившего Medium-риск (рассинхрон `works_in_zapros` и стадии), добавлена миграция 008 с триггером БД для гарантии консистентности.

**Почему:**
- Code-review нашёл edge-case: если в результате ошибки server action не завершился, флаг может рассинхрониться.
- Триггер — нижняя линия защиты, работает всегда.
- Фиксация на уровне БД предпочтительнее, чем надеяться на корректность кода.
