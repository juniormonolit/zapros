# Статусы и переходы

**Дата:** 2026-06-01

## Задача (`tasks.status`)

| Статус | Описание |
|--------|----------|
| `active` | Есть незакрытые позиции / активные запросы |
| `partially_closed` | Часть позиций закрыта или в финале |
| `completed` | Все позиции закрыты или брак, нет активных запросов |
| `archived` | Ручной архив или N дней без активности (фаза 2) |

## Позиция задачи (`task_items.line_status`)

| Статус | Описание |
|--------|----------|
| `free` | Не в активном запросе |
| `in_request` | Включена в отправленный запрос |
| `closed` | Победа по этой позиции |
| `rejected` | Брак по позиции |

Дубли в нескольких запросах **разрешены** — `in_request` может быть у нескольких параллельно.

### Автозакрытие дублей при победе

Когда запрос выигран и его позиции переходят в `closed`, все **другие открытые запросы**, содержащие те же `task_item`, **автоматически закрываются**:

- остальные открытые запросы по этой позиции → `outcome = cancelled`, `status = cancelled`;
- их invites → `lost` с причиной `other_supplier_selected`;
- в `request_events` пишется системное событие об автозакрытии;
- если у запроса есть и другие, ещё не выигранные позиции — он всё равно закрывается целиком (в MVP «1 запрос = 1 победитель», частичных побед нет).

## Запрос — канбан снабженца (`requests.status`)

| Статус | Колонка | Описание |
|--------|---------|----------|
| `draft` | — | Черновик до отправки |
| `new` | Новый | Только отправлен |
| `awaiting_responses` | Ожидаем ответы | Нет ни одного ответа |
| `has_response` | Есть ответ | ≥1 поставщик ответил, не все просмотрены |
| `clarification` | На уточнении | Активное уточнение |
| `in_progress` | В работе | Выбран сценарий работы / бронь |
| `lost` | Не прошли | Финал брак |
| `won` | Завершён (победа) | Скрытая группа по умолчанию |
| `no_response` | Без ответа | Все invites истекли по таймеру без ответа |
| `cancelled` | Отменён | Снят вручную или автозакрыт после победы дубля |

**Скрытые по умолчанию в канбане:** `lost`, `won`, `no_response`, `cancelled` (группа «завершённые/проигранные»). Показ через фильтр.

> **Колонка «Ответ получен» намеренно отсутствует:** по решению она слита с «Есть ответ». Признак «снабженец ещё не открывал ответ» отражается фильтром/бейджем «не просмотрено», а не отдельной колонкой.

### Правило вывода колонки запроса (агрегация invites)

У запроса один `status`, но invites бывают в разных состояниях. Колонка определяется по приоритету (сверху вниз — что встретилось первым, то и показываем):

1. `won` / `lost` / `cancelled` (финал запроса задан явно)
2. `in_progress` — снабженец перевёл запрос в работу
3. `clarification` — хотя бы один invite на уточнении
4. `has_response` — хотя бы один invite `answered` / `under_review`
5. `awaiting_responses` — есть активные invites, ответов нет
6. `no_response` — все invites истекли по таймеру, ответов не было

### Триггеры (авто)

| Событие | Переход |
|---------|---------|
| Отправка запроса | `draft` → `new` → `awaiting_responses` |
| Первый ответ поставщика | → `has_response` |
| Все invites `no_response` | → `no_response` |
| Снабженец «в работе» (сигнал) | → `in_progress` |
| Выбор победителя | → `won` |
| Брак без победителя | → `lost` |

## Приглашение — канбан поставщика (`request_suppliers.status`)

| Статус | Колонка поставщика |
|--------|-------------------|
| `new` | Новый запрос |
| `answered` | Дан ответ |
| `under_review` | На рассмотрении |
| `clarification` | На уточнении |
| `in_progress` | В работе |
| `lost` | Не прошли |
| `no_response` | Без ответа (таймер) |
| `won` | Победитель (скрыто у проигравших как lost) |

### Связь с действиями

| Действие | Invite | Запрос (агрегат) |
|----------|--------|------------------|
| Поставщик отправил ответ v1 | `new` → `answered` | → `has_response` |
| Снабженец открыл ответ | `answered` → `under_review` | — |
| Снабженец запросил уточнение | → `clarification` | → `clarification` |
| Таймер 10 р.д. без ответа | → `no_response` | пересчёт |
| Снабженец: в работе (сигнал) | → `in_progress` | → `in_progress` |
| Выбран победитель | победитель `won`, остальные `lost` | → `won` |

## Таймер «Без ответа»

- Объект: **`request_suppliers`**
- Срок: **10 календарных дней** от `sent_at` (праздники/выходные **не учитываем** — упрощённо)
- Часовой пояс: **Europe/Moscow**
- Срок настраивается в админке (`app_settings.response_deadline_days`, дефолт 10)
- **Пауза:** при переходе invite в `clarification` — `timer_paused_at`, `deadline_at` не тикает до выхода из уточнения (ответ поставщика или снятие снабженцем)
- Истечение: invite `status` → `no_response`; событие в `request_events`
- Если **все** invites запроса ушли в `no_response` без единого ответа → запрос уходит в архив (`tasks`/`requests` финализируются, скрыты из рабочего канбана)

## Победа и брак

**Принцип MVP: «1 запрос = 1 победитель».** Если по разным позициям нужны разные поставщики — снабженец создаёт отдельные запросы под эти позиции. Частичных (построчных) побед в MVP нет.

1. Снабженец выбирает **одного** поставщика → `winning_request_supplier_id`.
2. Остальные invites → `lost`, **одна** `reject_reason` на всех (enum).
3. **Снять победителя нельзя** в MVP.
4. Позиции запроса → `task_items.line_status = closed` для выигрыша.
5. Другие открытые запросы с теми же позициями **автозакрываются** (см. «Автозакрытие дублей при победе»).

## Блокировка ответа в финальных статусах

Когда invite в `lost` / `won` / `no_response` / (запрос `cancelled`), поставщик **не может** создавать или редактировать версии ответа и писать в тред. Проверка — на уровне серверного экшена и RLS.

### `reject_reason` (enum)

- `price` — не прошли по цене
- `lead_time` — сроки
- `availability` — наличие
- `other_supplier_selected` — выбрали другого
- `customer_cancelled` — отмена заказчика
- `no_response` — таймер
- `other` — + текст в `reject_comment`

## Быстрые сигналы снабженца (`request_events.event_type`)

| Тип | Смысл для поставщика |
|-----|---------------------|
| `signal_cheaper` | Есть цена дешевле |
| `signal_customer_price` | У заказчика есть цена дешевле |
| `signal_in_progress` | В работе (бронь/продажа) |

Не заменяют статус автоматически, кроме согласованного перехода в `in_progress` (опционально по кнопке «Применить статус»).

## Фильтр по умолчанию

**Группа стадий:** «Запрос в работе» = `new`, `awaiting_responses`, `has_response`, `clarification`, `in_progress` (без `lost`, `won`, `no_response`).
